# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Ecosistema de Salud Animal" — a pnpm-workspace monorepo for a veterinary/animal-management platform (product line: **HCE Animal** clinical records + turnero, and a future **Tropera** livestock module). All code, identifiers, comments and commit messages are in **Spanish** — keep new code consistent with that.

Workspaces (`pnpm-workspace.yaml`): `apps/*` (`backend`, `web`, `mobile`) and `packages/*` (not created yet).

## Commands

Run from repo root unless noted.

```bash

# Dev (backend :3000 + web :5173 together)
./dev.sh
# or individually:
pnpm --filter backend start:dev
pnpm --filter web dev

# Backend build / prod
pnpm --filter backend build

# Backend tests
pnpm --filter backend test            # jest (unit specs, e.g. codigo-legible.util.spec.ts)

pnpm --filter backend test:animales-demo
pnpm --filter backend test:personas-demo
pnpm --filter backend test:hce-demo

pnpm --filter backend test:plataforma-demo
pnpm --filter backend test:roles-demo
pnpm --filter backend test:macros-demo
pnpm --filter backend test:indicaciones-demo
pnpm --filter backend test:tropera-demo   # covers all of Tropera: F1.1-F1.6 core + Fase E (E.1-E.6) individual tracking
pnpm --filter backend test:caja-demo

# each *-demo script runs a self-contained flow against an in-memory PGlite instance
# (creates its own schema/tables) — no running server or DB needed. 18 suites total as of
# 2026-09-03; when a shared table (organizaciones, consultas, planes, ...) gains a column,
# run ALL 18, not just the one you're touching — `caja-flow.demo.ts`/`hce-flow.demo.ts` and

# DB (Drizzle)
```

`apps/mobile` is a full Expo Router app wired to the backend's `sync/` engine via WatermelonDB — see **Mobile architecture** below. It has its own `apps/mobile/CLAUDE.md` (redirects to `AGENTS.md`, which says to read the versioned Expo v57 docs before writing mobile code) — treat that app's conventions independently.

⚠️ If you start a backend against a **different** `DATABASE_PATH` than the user's (e.g. a throwaway PGlite dir for isolated testing), kill it by exact PID (`lsof -t -i :3000 | xargs kill -9`) when done — `pkill -f "nest start --watch"` **does not match** the process once `nest build` has run and something later starts it as `node dist/src/main`, so a stray test backend can silently keep holding the port (pointed at the wrong database) while the user's own backend fails to start or a later one binds to a different port instead. This has actually happened and cost real debugging time — always verify with `lsof -i :3000 -sTCP:LISTEN` and check the listening PID's `DATABASE_PATH` (`/proc/<pid>/environ`) before assuming which backend is live. Never run two processes against the same PGlite directory concurrently — it's single-process, not designed for concurrent access; stop the running server before applying any direct DDL/data fix to `apps/backend/pgdata`.

## Backend architecture (`apps/backend`)

Single NestJS API serving the whole ecosystem — not split per product. Modules are grouped by **database schema**, mirrored in `src/database/schema/*.ts`:

- `core/` → schema `core`: `auth` (login/register + `POST /auth/refresh`, stateless refresh token — same `JWT_SECRET`, payload `{ sub, tipo: 'refresh' }`, `JwtAuthGuard` rejects it if used as an access token), `especies`, `personas` (dueños), `animales` (pacientes), `usuarios` (miembros de la organización — `GET /usuarios` lists them; `POST /usuarios` is **self-service alta** by the org's own `propietario`/`admin`, 2026-09-03, respects the plan's per-role cupo via `common/verificar-limites-roles.ts` — distinct from the super-admin-only alta in `admin/`; `GET /usuarios/limites-plan` exposes cupo/usados per role for the wizard; `PATCH /usuarios/:id/password` resets a member's password, org-scoped `propietario`/`admin` only, not the platform `SuperAdminGuard`). Since 2026-09-05, `auth/` also has "olvidé mi contraseña": `POST /auth/forgot-password` (email, always resolves the same whether the account exists or not — no user enumeration) and `POST /auth/reset-password` (token + nueva password), both public, no guards. The token is a stateless JWT, same pattern as `PortalTokenService` below but `scope: 'reset_password'` and a 30-minute expiry; since there's no token table to mark one used, invalidation instead compares the token's `iat` against a new `usuarios.password_changed_at` column — any reset link issued before the last password change is rejected. The actual email send goes through `common/mail/mail.service.ts` (Resend SDK, `RESEND_API_KEY` env var) — with no key configured it just logs the link instead of sending, so local dev works without a Resend account. **Known gap**: `MAIL_FROM` still points at Resend's sandbox domain (`onboarding@resend.dev`), which in sandbox mode only delivers to the Resend account's own inbox — a real domain needs verifying in Resend before this reaches actual users (see `docs/Plan_Despliegue.md`).
- `hce/` → schema `hce`: `consultas` (create/read/update/soft-delete; `costo` numeric, **required** in `CreateConsultaDto` since 2026-09-03 — nullable in the DB for legacy rows, 0 is valid for a cortesía; deliberately does **not** auto-create a `caja.cobros` row, stays a clinical-record-only field, same loose-coupling as the F4.3 dispensa), `vacunaciones` (registrar/historial/recordatorios; the `producto` field is free text so it already covers desparasitaciones/other prophylactics — there's no separate `tipo` column), `turnos`, `carnet` (`@react-pdf/renderer`, queries real data via Drizzle; **two distinct PDFs, both built from the same `buildData()`**: `GET /animales/:id/carnet.pdf` — a CR80-sized wallet card, `carnet.document.ts` — with just identification + QR, and `GET /animales/:id/ficha.pdf` — a full A4 sheet, `ficha.document.ts` — with patient/owner data and the vacunaciones table, printable whether it's empty or full), and `hce/portal/` — the **public** dueño surface: `GET /portal/c/:codigo` (no guards, código legible from the QR is the credential; also exposes `fotoUrl`, read-only — see `portal/` below for the write path). Since 2026-09-04, `hce/catalogo-vacunas/` and `hce/catalogo-diagnosticos/` (registered flat in `hce.module.ts`, no per-feature module file — small enough not to need one) expose `GET /hce/catalogo-vacunas?especieId=` / `GET /hce/catalogo-diagnosticos?especieId=` against two new global reference tables (`catalogo_vacunas`/`catalogo_diagnosticos`, seeded from a fixed JSON list per species via `scripts/seed-catalogo-{vacunas,diagnosticos}.mjs`, idempotent). These are **suggestions only**, not a closed vademécum — the "Producto"/"Diagnóstico" fields on `vacunaciones`/`consultas` stay free text; the web/mobile search components just prefill from a match, they never restrict input to what's in the catalog (explicit product decision — a first cut used a closed `<select>`, replaced after user feedback that the list was a guide, not a gate).
- `admin/` — platform-level (super-admin only, `SuperAdminGuard`): crear organizaciones, gestionar membresías, `planes/` (CRUD; `activo` doubles as "disponible para altas nuevas" — `SolicitudesService.crear()` and `AdminService.setAcceso()` both reject assigning/requesting an inactive plan). **Home de facturación** (2026-09-03): `organizaciones.fechaActivacion` (falls back to `createdAt`) drives `AdminService.resumenPagos()`/`estadisticas` — próximo vencimiento (same day-of-month as activación, compares dates not datetimes so "due today" doesn't skip a month) and "¿pagó este mes?" against the new `plataforma.pagos` table (manual entries, no payment gateway integration); `gananciasPorPeriodo()` sums by calendar month. Web: `AdminPage.tsx`'s "Home" tab is now the panel's landing section.
- `solicitudes/` — public sign-up requests; this is what the web's `LoginPage` actually calls now, not `AuthService.register` (still present, unused by the web). Since 2026-09-03 the DTO only accepts `tipo: 'crear'` (the web dropped the "unirse a organización existente" option; the backend still holds `tipo: 'unirse'` data/approval-path for any solicitud already pending, just can't accept new ones) — `nombre`/`apellido`/`telefono`/`dni` all required now, plus a required `planId` (validated against `plataforma.planes.activo`, same rule as above). `GET /solicitudes/planes` (public, no guard) lists the pickable ones. Approving a `'crear'` solicitud now writes the chosen `planId` **and** sets `fechaActivacion: now()` onto the new organización — no more manual admin follow-up per new org.
- `portal/` (top-level, distinct from `hce/portal/`) — the **magic-link** dueño surface: staff issues access (`PortalTokenService`, `POST /portal/acceso/:personaId`, from a button in `PersonasPage.tsx`), the dueño then reads `/portal/resumen` and requests turnos via `/portal/turnos` — both authenticated by the `X-Portal-Token` header (`PortalGuard`), **not** `Authorization: Bearer` and not a query param, even though the link itself carries the token as `?token=` in the URL. Since 2026-09-03, `POST /portal/animales/:animalId/foto` (multipart, `FileInterceptor` + `multer` diskStorage) lets the dueño upload/replace a mascota's profile photo — verifies ownership same as `solicitarTurno()`. File lands in `uploads/animales/` **relative to `process.cwd()`, not `__dirname`** (`nest start --watch` runs the compiled JS in `dist/`, so `__dirname`-relative paths there resolve inside `dist/` and get wiped on rebuild — this bit once already, see `docs/CHANGELOG.md` 2026-09-03) and is served statically via `app.useStaticAssets()` in `main.ts` (also `process.cwd()`-relative) at `/uploads/...`; `BACKEND_PUBLIC_URL` env var (default `http://localhost:3000`) is what gets baked into the stored `fotoUrl`, so it **must** be the real public origin in prod. Client-side compression (`utils/comprimirImagen.ts`, canvas resize to 800px + JPEG quality 0.75) happens before upload — there's no image-processing library on the backend (no sharp), so sending a smaller file was the only option. The código-based public portal (`hce/portal/`) deliberately has **no** upload endpoint — no token there at all, the printed código itself is the credential, and allowing writes on that surface would lower the bar too far.
- `caja/` → schema `caja`: `cajas` (una caja diaria por organización; `abrir()` rejects if one's already open) + `cobros` (ingresos; `veterinarioId` optional, for honorarios liquidation) + `egresos` (kept in a separate table on purpose, never listed together with cobros). **Apertura rápida** (2026-09-03): `CobrosService.crear()` no longer rejects when no caja is open — it opens one itself (`montoInicial: 0`) via `CajasService.abrir()` called directly (service-to-service, bypassing that method's own `RolesGuard` — fine, since only `propietario`/`admin`/`recepcion` can reach `CobrosService.crear()` in the first place, the same roles who could open a caja by hand). `EgresosService.crear()` deliberately did **not** get the same treatment — an egreso isn't a good reason to spontaneously open the day's caja. `GET /caja/cajas/estadisticas?desde&hasta` (2026-09-03, `propietario`/`admin` only) aggregates cobros/egresos in JS over the fetched rows (no SQL `GROUP BY` — fine at this volume): totals, neto, cantidad de cajas, por método de pago, por día.
- `sync/` (`sync.core.ts` + `sync.service.ts`) — offline pull/push sync engine, WatermelonDB-compatible contract, fully implemented and tested (`test:sync-demo`); no consumer yet since `apps/mobile` isn't wired to it. Does not cover `tropera.*` yet.
- `tropera/` → schema `tropera`: `establecimientos` (CRUD) + `existencias` (headcount by category — `vaca`/`toro`/`ternero`/`ternera`/`vaquillona`/`novillo`, **aggregate counts, not one row per animal**; `ExistenciasController` at `tropera/establecimientos/:id/existencias` like `carnet` nests under `animales/:id`, plus a second controller `ExistenciasResumenController` at the unrelated `GET tropera/existencias` — org-wide, all establecimientos, for the panel consolidado; the two share a service but live at deliberately non-overlapping routes) + `movimientos` (`nacimiento`/`compra`/`muerte`/`venta`/`traslado` — `POST` adjusts `existencias` **in the same transaction** it inserts the ledger row; a baja that would leave `cantidad` negative throws instead of partially applying) + `eventos` (`vacunacion`/`desparasitacion`/`tratamiento`/`servicio`/`diagnostico_prenez`/`destete` — **does not touch `existencias`**, pure log; `categoria`/`cantidad` optional, roles include `veterinario` unlike the other three tropera modules). No `parto` event type — a birth is a `nacimiento` movimiento, modeling it twice would be redundant while hacienda stays aggregate-only.
- `farmacia/` → schema `farmacia`: `productos` (vademécum CRUD, `categoria`/`unidad`/`presentacion` free text at the DB level — a real vademécum is too varied for a closed enum, unlike Tropera's 6 fixed categories; the closed-list UX the web now enforces on these three fields is a **frontend-only** constraint, see below — plus `esMedicamento`/`esFraccionable` booleans and `precioCompra` numeric, added 2026-09-01) + `stock` (one row per producto; `GET /farmacia/stock` returns **all** active productos for the org with their cantidad via `LEFT JOIN` + `coalesce`, in one call — simpler than Tropera's equivalent since there's no establecimiento layer here; `PATCH .../stock/:productoId` is the direct correction) + `movimientos` (`compra` alta / `uso`, `vencimiento`, `merma`, `venta` baja — same transactional-ledger shape as `tropera/movimientos`, rejects a baja that would go negative; quantities are still integers throughout — "fraccionable" is informational only, doesn't unlock decimal cantidades). Write roles: `propietario`/`admin`/`veterinario` (no `capataz`/`recepcion` — clinical, not field or front-desk); cobros/venta de mostrador is `propietario`/`admin`/`recepcion` instead (see `caja/`). `movimientos_stock` has an optional `consulta_id` FK (F4.3, 2026-08-28): a dispensa is **not** a separate entity, it's a `tipo: 'uso'` movimiento with `consultaId` set — `MovimientosService.crear()` validates the consulta belongs to the org before inserting, and `listar()`/`GET .../movimientos` accepts an optional `consultaId` filter alongside `productoId`. Still deliberately out of scope: a real FK from `hce.vacunaciones.vademecum_id` to `farmacia.productos.id` (still just a logical reference, no constraint) — dispensing stays tied to the consulta, not to a specific vacunación. Since 2026-09-04, `farmacia/vademecum-senasa/` (its own module, `VademecumSenasaModule`) exposes `GET /farmacia/vademecum-senasa?buscar=` (ilike, limit 20) against a new global reference table (`vademecum_senasa`, 7003 rows seeded from a real SENASA CSV via `scripts/seed-vademecum-senasa.mjs`, **no unique constraint** on `certificado` — ~245 legitimate duplicates in the source data). Same "suggestion, not a gate" rule as the vaccine/diagnosis catalogs above — F4.1 in the Roadmap ("import SENASA") is covered by this reference lookup, not by a bulk import that makes every org's `farmacia.productos` real stock out of it (that would be wrong — a clinic's actual vademécum is a subset it stocks, not the whole national list).
- `analitica/` → schema `plataforma`, table `eventos_uso` (`tipo`: `'pantalla'` | `'accion'`, `organizacionId`, `usuarioId` nullable, `nombre` free text, `createdAt`): `POST /analitica/eventos` (any authenticated role, `TenantGuard` only) is a plain fire-and-forget insert — the web and mobile clients call it after key actions/screen views and swallow any error (`.catch(() => {})`), it must never break the action it's instrumenting. `AdminService.resumenAnalitica(desde?, hasta?)` (`admin/admin.service.ts`) aggregates it for the super-admin panel: top pantallas/acciones (`groupBy` + `count(*)`, limit 15 each), top organizaciones (limit 10), total count — same `gte`/`lte`-on-`createdAt` date-range pattern as `CajasService.estadisticas()`, defaults to the last 30 days. See `AdminPage.tsx`'s "Analítica" tab below for the consumer.

`portal/` and `hce/portal/` each define a class literally named `PortalController`/`PortalService`/`PortalModule` — same names, two unrelated features (public code-based read-only vs. staff-issued magic-link with turno requests). Don't assume "the" `PortalService` — check which directory you're in.

**Request guard chain** (order matters, later guards depend on state set by earlier ones):

1. `JwtAuthGuard` — validates the Bearer token, sets `req.user` (`{ sub, email }`)
2. `TenantGuard` — reads header `X-Organizacion-Id` (organization is **always** in the header, never the body), checks the caller has an active `membresia` there and the org is active, sets `req.organizacionId` and `req.rol`
3. `RolesGuard` + `@Roles(...)` — compares `req.rol` against the roles allowed on the handler

Access these via param decorators instead of `@Req()`: `@CurrentUser()`, `@CurrentOrg()`, `@CurrentRol()` (`src/common/decorators/current-context.decorator.ts`). Any module using these guards needs `JwtService`, so import `AuthModule` into it (see `usuarios`, `animales`, `turnos`).

Roles: `propietario`, `admin`, `capataz`, `veterinario`, `recepcion`. Separately, `SuperAdminGuard` gates the `admin/` module using `SUPERADMIN_EMAILS`.

**Database access** — Drizzle ORM, SQL-first, injected via the `DRIZZLE` token (`src/database/drizzle.provider.ts`):
- Driver picked at runtime by `DATABASE_DRIVER` env var: `pglite` (default for local dev — Postgres embedded in-process, no install needed, persisted at `DATABASE_PATH`) or `node-postgres` (real Postgres, prod).
- All schema files import from `src/database/schema/index.ts`.
- Tables use soft delete (`deleted_at`) and `updated_at` throughout — this is what the `sync/` engine relies on.
- Species-specific animal data (`animales.datos_especificos`, JSONB) has no fixed backend schema; the field catalog lives in the frontend (see below).

**Migrations**: hand-authored Drizzle schema → `drizzle-kit generate` writes SQL into `db/migrations/` (versioned, committed) → `drizzle-kit migrate` applies to real Postgres (does not seed), or `scripts/init-local-db.mjs` applies + seeds `especies` for local PGlite dev (this one ignores `meta/_journal.json` — reads the directory and applies `.sql` files in alphabetical order).

`db/migrations/` is a **single squashed migration** (`0000_ecosistema_base.sql`, 3 schemas / 8 enums / 13 tables) as of 2026-08-28 — two earlier migrations had been hand-added without ever going through `drizzle-kit generate`, which left `meta/_journal.json` out of sync (`drizzle-kit migrate` against real Postgres would have silently skipped them). Fixed by squashing rather than hand-reconstructing the missing journal entries, since no real-Postgres deploy exists yet, so there was no applied history to preserve. Full account in `docs/CHANGELOG.md`. Going forward `db:generate` should behave normally — if it ever asks for a manual rename/journal-tag fix again, something broke and it's worth finding out why before repeating the old workaround.

The migration **has** since been run against a real Postgres (locally, v12, 2026-08-28 — see `CHANGELOG.md`), which caught two things PGlite never would:
1. `gen_random_uuid()` (what every `.defaultRandom()` uuid column compiles to) is only native from **Postgres 13 on**; older versions need the `pgcrypto` extension — but PGlite's WASM build doesn't have that extension available at all (the function is already native there, so it never needed it). The migration now opens with a `DO $$ ... EXECUTE 'CREATE EXTENSION IF NOT EXISTS "pgcrypto"' ... EXCEPTION WHEN OTHERS THEN NULL END $$` — best-effort, so it's silently skipped wherever it's unavailable-but-unneeded instead of aborting the whole migration (that's exactly what an unguarded `CREATE EXTENSION` did to PGlite the first time this was "fixed").
2. `core.especies` comes back empty after `drizzle-kit migrate` — seeding was PGlite-only. Fixed with `scripts/seed-especies.mjs` (`pnpm db:seed`), which picks pglite/node-postgres the same way `drizzle.provider.ts` does and is idempotent; `init-local-db.mjs` now imports its `sembrarEspecies()` instead of duplicating the `INSERT`. If you ever write another Node script meant to be run both directly and imported, don't gate the `main()`-style entry check with `import.meta.url === 'file://' + process.argv[1]` — `import.meta.url` percent-encodes characters like spaces, `process.argv[1]` doesn't, so the comparison silently fails on any path containing one (this repo's does). Use `fileURLToPath(import.meta.url) === process.argv[1]` instead.

⚠️ **A new schema/table never reaches the user's real `apps/backend/pgdata` on its own.** `nest start --watch` reloads *code* on save, not *DDL* — this has bitten Tropera and Farmacia both, same failure mode each time (500s, `relation "..." does not exist`) until the new migration's DDL was applied by hand. If you add a schema/table, either walk the user through `db:local-init`-equivalent steps, or (what's been done several times now) stop their real backend by exact PID, apply just the new migration file's statements directly against `./pgdata` with a one-off PGlite script (verify row counts on a couple of existing tables before **and** after, to catch corruption from any accidental concurrent access), then restart. Don't skip the before/after integrity check — PGlite is single-process, not safe for two processes touching the same directory at once. Most recent examples: migrations `0020`–`0025` (2026-09-03: `organizaciones.fecha_activacion`, `plataforma.pagos`, `solicitudes.plan_id`, `hce.consultas.costo`, plus two more from farmacia/sync work) — all plain nullable `ADD COLUMN`/`CREATE TABLE`, each applied this way with a confirmed before/after row count match; ask before doing this since it means killing the user's live process, even briefly.

## Web architecture (`apps/web`)

React + Vite, plain CSS (`src/styles.css`, no UI framework). Structured by **pages**, not features.

- Session (`{ token, refreshToken, organizacionId, rol }`) is owned by `useSesion` (localStorage-persisted) and instantiated once in `App.tsx`, which is the single source of truth. Other modules don't read session storage directly — `App.tsx` pushes it down explicitly (e.g. `configurarSesionTurnos(sesion)` for `api/turnos.ts`). Follow this pattern for any new API client instead of reaching into `localStorage` directly.
- `api/client.ts` sends the token as `Authorization: Bearer` and org as `X-Organizacion-Id` on every call; talks to `VITE_API_URL` (default `http://localhost:3000`).
- Refresh is silent: `api/client.ts` and `api/turnos.ts` each implement their own 401-triggers-`POST /auth/refresh`-then-retry-once logic (duplicated on purpose, matching how these two files already duplicate session handling), and each calls back into `App.tsx` (`configurarRefrescoSesion`/`configurarRefrescoSesionTurnos`) so `useSesion.actualizarTokens()` persists the new pair. A new API client that needs auth should follow the same shape rather than assuming `client.ts`'s session store is shared.
- Home screen depends on role: `propietario`/`admin`/`recepcion`/`veterinario` land on the turnero (`ROLES_TURNERO` in `App.tsx`); others land on Animales.
- Per-species form fields (`config/especieDatos.ts` + `components/CamposEspecie.tsx`) are a frontend-only catalog rendered dynamically and persisted into `animales.datosEspecificos` — add/remove a species field there and it flows through alta/edición/ficha automatically.
- `main.tsx` does its own URL-based routing (no router lib): `/admin` → `AdminPage` (separate super-admin login), `?token=` → `PortalAccesoPage` (magic-link, all of a dueño's animales), `/c/:codigo` or `?c=` → `PortalDuenoPage` (public, one animal), `?resetToken=` → `ResetPasswordPage` (2026-09-05, "olvidé mi contraseña" — see `auth/` in the backend section above), everything else → `App.tsx`. All the query-param routes are distinct and don't collide. When there's no session, `App.tsx` itself branches once more: `/login` → `LoginPage`, anything else → `LandingPage.tsx` (2026-09-04, public marketing page — hero, features, dynamic pricing sourced from `listarPlanesPublicos()`, every CTA sends to `/login` or `/login?plan=<id>`, which `LoginPage.tsx` reads on mount to preselect that plan and start in modo registro).
- Quick-create pattern for a missing related record: when a form needs a `personaId` that might not exist yet (alta de animal in `PacientesPage.tsx`, alta de paciente in `TurnosPage.tsx`), the `<select>` gets a `'__nuevo__'` sentinel option that reveals inline nombre/apellido/celular/DNI fields; on submit, `POST /personas` runs first and its id feeds the main create call. Reuse this pattern rather than inventing a modal/redirect when the same need comes up elsewhere (e.g. a future alta de turno without existing paciente).
- `TroperaPage.tsx` follows the same list→detail shape as `PacientesPage.tsx`/`PacienteDetallePage.tsx` (a "seleccionado" establecimiento swaps the whole view rather than nested routing). Its existencias table is per-category rows, each with its own input + save button hitting `PATCH tropera/establecimientos/:id/existencias` individually — there's no batch-save. Two ways to change a count and they mean different things: that direct `PATCH` is an unaudited correction (no ledger row), while the movimientos form (`POST tropera/movimientos`) is the tracked path with history — don't blur them when extending this page. The list view (not the detail) also renders `ResumenConsolidado`, a matrix built client-side from `api.existenciasConsolidadas()` (org-wide, `GET tropera/existencias`) crossed with the already-loaded establecimientos list — only shown with 2+ establecimientos. Every write action in this file (18 call sites as of 2026-09-04, one per form/mutation — `tropera-establecimiento-crear`, `tropera-movimiento-crear`, `tropera-existencia-corregir`, etc.) fires `api.registrarEvento(sesion, 'accion', '<nombre>')` right after the API call succeeds — this file was the last one instrumented when usage analytics was rolled out app-wide, so it's the most complete reference for the naming convention (`<módulo>-<entidad>-<verbo>`) if you add a new Tropera action.

What's left of `utils/exportar.ts` (the `ColumnaExport` type + `valorDe` helper, still used by `DrawerTabla.tsx`'s drill-down tables) moved to `utils/columnasTabla.ts`.
- **Don't wrap a `Field`/label-style helper component in a real `<label>` element if its children can contain other clickable elements** (a suggestions dropdown, buttons). A `<label>` intercepts clicks on any descendant to refocus its first associated form control, which can swallow clicks meant for those other elements before React's handler runs. `TurnosPage.tsx`'s `Field` was a `<label>` wrapping both a search `<input>` and, conditionally, an unrelated suggestions list — switched to `<div>` (the CSS only ever targeted the `.hu-field` class, not the tag). If you add a new `Field`-like helper, default to `<div>` unless every one of its children is guaranteed to be exactly one form control.

Los targets de pasos "profundos" (no sólo ítems del nav, que siempre están montados) sólo apuntan a botones que se renderizan sin condicionar por estado de carga/selección (ej. `[data-tour="turnos-nuevo"]`, `animales-nuevo`, `tropera-nuevo`, todos en la cabecera de sus páginas) — si el target no existe en ese momento (`EVENTS.TARGET_NOT_FOUND`), el tour salta ese paso en vez de trabarse.

## Mobile architecture (`apps/mobile`)

Expo Router (file-based routing) + WatermelonDB (offline-first local DB, synced against the backend's generic `sync/` engine — see `apps/backend`'s `sync/` bullet above). A first working build was installed on a real Android phone and used for hands-on testing starting 2026-09-04; this is not a scaffold, it's the same product surface as the web (Huella side) minus Tropera, reshaped for a phone.

- **Sync**: `db/sync.ts` wraps WatermelonDB's `synchronize()` against `api.pull`/`api.push` (`api/client.ts`), driven by `db/SyncContext.tsx` (`useSyncContext()`) — sync is fully automatic (on mount, on reconnect, pull-to-refresh in list screens), there is no manual "sync now" tab; an explicit sync button was tried and dropped per user feedback that it should just work in the background. `db/schema.ts`/`db/migrations.ts` mirror the backend's Drizzle schema for every synced table (`animales`, `personas`, `consultas`, `vacunaciones`, `turnos`, all of `tropera.*` and `farmacia.*`'s tables that have a WatermelonDB model) — bump the schema version and add a migration step whenever a synced table gains a column (e.g. `consultas.costo`, schema v6).
- **Session**: `auth/SesionContext.tsx` (`useSesionContext()`) is the single source of truth, same role as `useSesion`/`App.tsx` on the web. `api/client.ts` is a deliberate near-port of the web's `api/client.ts` — same `pedir()`-with-silent-401-refresh shape, same fire-and-forget `registrarEvento`, adapted for React Native (`process.env.EXPO_PUBLIC_*` instead of `import.meta.env`, no shared session store to reach into).
- **Routing gotcha — `(app)/index.tsx` is a redirect shim, not a real screen.** Expo Router treats `(app)` as a route *group* (no URL segment of its own), so both `/` and `/(app)` resolve to the literal file `app/(app)/index.tsx` regardless of the `<Tabs initialRouteName>` you set — this caused a real bug (app always landing on the wrong tab on cold start). Fixed by renaming the actual "Establecimientos" screen away from `index.tsx` (now `establecimientos.tsx`) and making `index.tsx` a pure `<Redirect href={sesion.huellaActiva ? '/(app)/home' : '/(app)/establecimientos'} />`. If you ever add a screen literally named `index.tsx` inside a route group, expect this same collision.
- **Tab gating**: `app/(app)/_layout.tsx` hides tabs the org doesn't have active (`href: null` per tab, keyed off `sesion.huellaActiva`/`troperaActiva`) — a tab for a solución the org hasn't bought must never render, not just redirect away from it.
- **Analytics**: same `plataforma.eventos_uso` pipeline as the web (see `analitica/` in the backend section). `api.registrarEvento(sesion, tipo, nombre)` in `api/client.ts` is the call; screen views are instrumented once, centrally, in `app/_layout.tsx`'s `RootNavigator` — a `useEffect` keyed on `useSegments()` (filtered to drop route-group segments like `(app)`, and skipping the bare `(app)` redirect-shim moment) fires `'pantalla'` events on every route change, so individual screens don't each need their own tracking `useEffect`. Actions are instrumented at the call site, same convention as web (`'home-consulta'`, `'turno-atender'`, `'consulta-crear'`, `'foto-subir'`, `'producto-crear'`, `'animal-crear'`, `'stock-venta'`/`'stock-ingreso'` — the latter two live in the shared `db/altaProducto.ts`/`db/altaPaciente.ts` helpers so both call sites that reuse them get the event for free instead of duplicating it).
- **Reusable components worth knowing before adding a new form**: `components/SelectorDueno.tsx` (dueño search-or-create, always resolves to either an existing `persona.id` or a full `NUEVO_DUENO` payload with required DNI — a dueño is mandatory, unlike the web's older optional-dueño alta); `components/BuscadorCatalogoVacunas.tsx`/`BuscadorCatalogoDiagnosticos.tsx` (mobile port of the web's search-with-suggestions pattern described above — same rule, no suggestions shown until the user types); `components/CampoColapsable.tsx` (collapsible field wrapper with a filled/empty dot indicator, used on the consulta form so a long form doesn't read as intimidating all at once); `components/CampoFecha.tsx` (2026-09-05, native date picker via `@react-native-community/datetimepicker` — replaced a plain "type AAAA-MM-DD" text field for vacunación's "próxima dosis"; Android shows a modal dialog that closes itself, iOS stays inline until "Listo" is tapped, hence the platform branch in `onChange`); `components/FotoAnimal.tsx` (camera/gallery picker + upload, see the native-upload gotcha below).
- **`db/altaPaciente.ts` / `db/altaProducto.ts`**: shared offline-alta helpers (not backend calls — plain WatermelonDB `create()` inside `database.write()`) used by both the Home quick-access flow and the dedicated screens, so an animal/producto created inline from a search field ("＋ no aparece: crear nuevo") and one created from its own screen go through the same code path and both fire the same analytics event.
- **Native module gotchas** (bit twice, worth remembering before adding another native dependency):
  - `npx expo install <pkg>` runs plain `npm install` in this pnpm monorepo, not `pnpm add` — it drops a stray `apps/mobile/package-lock.json` and can leave `node_modules` in a broken state. After running it, delete that lockfile and run `pnpm install` from the repo root to let pnpm re-resolve properly (`apps/mobile/.npmrc` has `node-linker=hoisted`, so packages hoist to the **root** `node_modules`, not a per-package one — that's correct behavior in this mode, not a bug, once you know to expect it).
  - Adding a native module means the JS bundle isn't enough — you need a native rebuild (`npx expo run:android`, needs `ANDROID_HOME`/`ANDROID_SDK_ROOT` set and a connected/authorized device via `adb devices`), not just a Metro reload. Expo SDK 57 replaced RN's classic `fetch`/`FormData` with its own runtime ("winter"), which does **not** support the `{uri, name, type}` file-upload convention (`Unsupported FormDataPart implementation`) — file uploads (`api.subirFotoAnimal`) go through `expo-file-system`'s native `File.upload()` instead of `fetch`+`FormData`.
- **Forgot password on mobile**: no in-app reset form — `login.tsx`'s "¿Olvidaste tu contraseña?" only collects the email and calls `api.olvidePassword()`; the actual password-setting happens by opening the emailed link in the phone's browser, which lands on the same `ResetPasswordPage` the web uses. Deliberately not duplicated as a native screen since it's a one-off, connectivity-required action.
- **Turnos** (`app/(app)/turnos.tsx`): Hoy/Próximos/Todos client-side time filter, plus an "Atender" button (`ROLES_ATIENDEN` = veterinario/propietario) on `confirmado`/`reprogramado` rows that flips `estado` to `atendido` via a local `database.write()` and opens the ficha with `?seccion=consulta` — same flow as the web's `HuellaHomeSection.tsx`, reproduced here.
